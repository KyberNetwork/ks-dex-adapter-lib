# Efficient PropAMM listing adapter

Executes exact-input trades of an Efficient PropAMM listing, using input already held by the adapter, either through the listing's own door or through the front the listing trades on. Each listing has its own door: one contract, one pair (`TOKEN0`, `TOKEN1`), either direction. Output is paid directly to the supplied recipient; unused input is zero on success, since every route fills the whole input or reverts. Native ETH is unsupported.

A listing's door sits at a CREATE2 address its door factory derives from the listing id (`doorOf(listing)`); anyone may open it (`open(listing)`). The companion `efficient-prop` source lists one pool per door, with the door as the pool address, and carries the door, the front, the listing and the fill mode in the pool's data.

## Data and fill modes

Encode `data = abi.encode(door, front, listing, mode)`: four words, the listing a 24-bit id. The data is the companion source's own, so the adapter decodes its words as they are and checks only the mode: a mode other than 0, 1 or 2 reverts with `UnknownFillMode(mode)`.

- **Mode 0, the door.** The adapter approves the door for exactly `amountIn` and calls its pull entry, `swapFrom(tokenIn, tokenOut, amountIn, 1, recipient, block.timestamp)`. The door pulls exactly that amount, so the approval ends at zero. Where the listing names a pool to pay, the input moves once, from the adapter straight to that pool. Each settled fill logs one `Swapped`: on Base the door logs it, and on a builder chain the listing's quote contract logs it with the door as `sender` (see below).
- **Mode 1, the front.** The adapter reads `front.payPoolOf(listing)`.
  - Where it names a pool (a listing with no credit mode), the adapter transfers `amountIn` to that pool and calls the paid entry, `swapExactInPaid(tokenIn, tokenOut, amountIn, 1, recipient, block.timestamp, listing)`, in the same frame with no call between. No approval is given. The front proves the payment by the pool's balance: at least its tracked custody plus `amountIn`. Input the pool already holds untracked (a donation, an overpayment) counts toward that proof, so a fee-on-transfer input, which lands short, reverts the hop unless the pool's untracked balance covers the fee, and the fill then spends that balance. The door's pull entry pays the same pool and calls the same paid entry, so mode 0 does the same where the listing names a pool.
  - Where it is zero, the adapter approves the front for exactly `amountIn` and calls the named entry, `swapSender`, with the same arguments. The front pulls exactly that amount, straight into the listing's pool, so the approval ends at zero.
- **Mode 2, a block door. Not live.** No source builds this mode's data yet, and no block door is deployed; the mode is here so that BNB Chain needs no second adapter. A block door is the venue takers following BNB Chain's PropAMM standard (BAP-710) call: push payment, and `swap`'s last argument a block number, the last block the swap fills in. The data's first word is the block door. The adapter transfers `amountIn` to it and calls `swap(tokenIn, tokenOut, amountIn, 1, recipient, block.number)` in the same frame with no call between, so nothing pushed is ever left at the door for another caller, and a refusal reverts the transfer with the rest of the hop. No approval is given. A block door fills through its router door, which picks the listing that pays most for the pair, so this mode is for a pool that is a block door's pair, not for a listing's door.
- **Mode 3 is left unused**, for a later mode that fills a signed firm quote. The adapter refuses it today, as any mode past 2 (`UnknownFillMode`).

The door and the front validate the pair and refuse a size the listing does not fill now with the listing's own error, which reverts the whole route; the adapter neither catches nor rewrites it, so a refusal after the paid route's transfer undoes the transfer with the rest of the hop. The enclosing Kyber router must enforce its overall minimum output and deadline: the adapter passes a minimum output of 1 and this block's timestamp. The adapter reads neither token symbols nor decimals, and does not support fee-on-transfer or rebasing tokens.

## Limit: the listing's tip cap

A listing has a tip cap: the most priority fee per gas (`tx.gasprice` above `block.basefee`) it fills at. The cap is the listing's own setting, chosen by its operator, and the door and the front refuse a fill above it with `TipCapped()`. Neither this adapter nor the source can change it, and a refusal reverts the whole route, so whether a route through this hop fills depends on the gas price the route is sent with. For a listing with no price source, or one whose sources are all approved (next section), the tip does not change the price.

- On Base the front is a storage build, where a desk's price stands only while its listing's cap is set. With a cap of 0 no price stands, so the listing fills nothing: its door refuses every size (`NoFill`) and the front every fill.
- On a front that is not a storage build, a cap of 0 means no cap: the listing fills at any tip.
- A fill tipping exactly the cap fills; one wei more reverts the route with `TipCapped()`.
- A quote by `eth_call` with no gas price sees a tip of 0, so a listing that fills prices the hop whatever its cap.
- A legacy transaction tips its whole `gasPrice` above the base fee, so it fills only up to a `gasPrice` of base fee + cap.
- The companion source keeps each listing's cap in the pool's state and in its meta (`tipCapWei`, wei per gas). It leaves out a listing whose nonzero cap is under its config's `minTipCapWei` (default 0: none left out). It keeps a listing whose cap is 0, which on Base quotes no size, so the source samples no price for it. A route sent with a tip above a listed cap still reverts.

## Limit: a listing's price source

A listing prices from its desk's posts, and a listing that reads a price source (a print, a session, a tied listing) also from the sources it is bound to. A source is any contract registered on the front, which anyone may register, and the listing's operator binds it. The source's code runs inside the quote and again inside the fill, and it can tell the two apart: by what the call reads of its transaction and block, and by state the fill has already changed when the source runs. The front holds its lock during a fill, and on the paid route the input is already at the pool. A source that tells them apart can fill a real transaction for less than an `eth_call` quoted, down to the route's minimum output. So approve a source only where its code cannot change and its answer comes from its own stored prices and the clock alone. For a listing with no source, or whose every source is approved, a fill pays what the door quotes from the same state.

The same holds for a listing's two tokens. Their code runs inside the fill and can tell it from a quote in the same ways, and neither the adapter nor the companion source screens them: the source lists a listing whatever its two tokens are. Route through a listing only where its tokens' code cannot change and moves exactly the amounts asked.

The companion source serves a listing that reads a price source only where every source it is bound to is on its config's list of approved sources for that front, and reads the binding again on every refresh; the list is empty by default, so only listings with no source are served until the source's config names the protocol's sources. Whatever the list holds, it does not serve a tied listing or a session listing with a closed phase. It does serve a listing whose live source is guarded. Such a source prices a fill at the worst, for the fill's side, of the prints its lane still holds, and a lane holds a replaced print for a short time after a post, so in the blocks of that hold the door can quote a size lower than it will once the hold ends, or refuse it, and a side at its output bound can refuse, in the first block after the hold, a size it filled inside it. The companion source quotes such a listing at no more than the door fills at any block up to the first after the hold, and leaves out a size the door refuses at any of them. The adapter cannot tell these kinds apart: it fills the listing the pool's data names.

## Base mainnet

This build is not deployed on Base. This section gains the front's and the listing-door factory's addresses with that deployment.

## Builder chains: Ethereum mainnet

On Ethereum the front is a builder build. A listing's quote contract holds its maker's quote for one block: the maker's relay entry writes the quote, with the pair's price update, and a builder places that entry in the block ahead of the fills it is for.

- **Both modes fill; mode 1 is the cheaper.** A listing's door is a forwarder to the front's own two entries, the ones mode 1 calls, so a fill pays the same output and meets the same refusals in either mode. Measured through this adapter's call frame on a fork of Ethereum holding the deployed build, mode 1 spends 29,785 to 32,931 gas less a fill on the three listings that read a price (145,207 to 160,941 against 176,133 to 193,812) and 31,749 to 37,144 less on the listing with a credit mode (a custody fill 156,864 to 158,047 against 188,613 to 195,191, a fill that borrows 945,731 against 982,826). Those are before refunds; mode 0 earns 19,900 more back a fill (the door's allowance, set and cleared in the transaction), so at the receipt mode 1 saves 9,885 to 13,031 and 11,849 to 17,244. The companion source's config names the mode per front and declares the gas of that mode. Mode 0 stays for an executor that will only approve a contract that cannot change: a door is immutable, where the front is a proxy.
- **The fill's log.** On a builder chain the listing's quote contract logs each settled fill's one `Swapped`, with the front's caller as `sender` (the door through mode 0, this adapter's caller frame through mode 1), the fill's tokens, amounts and recipient. The door logs none there. That log, at the contract the maker's entry writes, is how a builder matches a route's fill to the listing whose entry it places ahead of it, in either mode.
- **Gas limits.** A fill needs more gas in hand than it spends: the least gas limit that let a fill through this adapter was 21% to 29% above the gas its receipt reports (21% to 23% on the listings that read a price, 29% on the credit listing's custody fill, 24% on its borrowing fill), since each call down to the pool and its lending venue forwards at most 63/64 of the gas left. Set a route's limit at 1.3 times its expected gas or more, never from a receipt's gas used.
- **Exposure to `NoWord`.** A listing fills only in a block in which its quote contract's entry landed ahead of the fill. In any other block the door quotes no size (`NoFill`) and a fill reverts with the front's `NoWord()`. A route that lands in such a block reverts whole, and the taker pays the gas used up to the revert; the adapter cannot tell the block apart and neither catches nor rewrites the refusal. The one exception is a listing whose quote carries: there the quote may also fill in the next block, while its life and the listing's price age allow it. In the block after a carried quote the front refuses with `StalePull()`, in place of `NoWord()`, when the price update the quote rides on is past the listing's price age at that block, and with `AnchorExpired()` once the quote's own life has ended; the door's quote reverts `NoFill` in both cases, and the taker pays the gas either way. A price update is stamped before its block, so `StalePull()` is the refusal a taker meets there in practice, and the front checks it before `AnchorExpired()`.
- **Carried fills.** A fill carries only where all three hold: the listing's binding allows carry (the operator's setting on the listing), the maker's entry sets the carry bit on the quote, and the listing's fence is not `NONE`. With any of them off, no fill is carried and the exception above does not arise. A carried fill is dearer than a fill in the entry's own block. Measured through this adapter's call frame on the stable pair (the call frame as the companion source declares it: before refunds, the recipient already holding the output), a fill one block after its entry costs 2,419 gas more than a fill of the same quote in the entry's own block, on a price-read listing and on a quote-only listing alike: 191,454 sell and 194,120 buy against 189,035 and 191,701 on the price-read listing, and 181,115 and 183,581 against 178,696 and 181,162 on the quote-only listing. Against the stable pair's least first fills without carry (188,508 sell and 191,212 buy on the price-read listing, 178,421 and 180,925 on the quote-only one) the carried fill costs 2,656 to 2,946 more. These are the least seen across runs; same-size first fills vary by up to about 500 gas from run to run. Every figure of this paragraph is of the build before the deployed one. On a fork of Ethereum holding the deployed build (front `0x0000000000403aeB66691063CC2fD42E71d6AcD6`), the stable pair's price-read listing's least first fills without carry measure 190,596 sell and 193,812 buy through the same call frame. A carried fill has not been measured on that build, since no listing of the pool measured allows carry, and neither has a quote-only listing, since that pool lists none. The gas figures declared for the stable pair are for first fills in the entry's own block and do not include this. The adapter's tests run with the carry bit clear.
- The listings' tip cap on Ethereum: a cap of 0 means no cap (see above).

## Tests

The unit tests run both directions through a mock door and a mock front, through the door, the front's paid entry and its named entry, and keep one test for each safety rule: the payment and the paid call in one frame with no call between, a refusal after the payment passed through unchanged, through the door and through the front, so that the revert undoes the payment, no approval left on the door or the front and no input spent past `amountIn`, a fill mode the adapter refuses, and a listing id past 16 bits passed whole. Mode 2 has its own unit tests against a mock block door that keeps the real door's rules for the deadline and the payment: both directions at the door's quote with this block as the last block, the push and the swap in one frame, nothing left at the door, no approval given, a refusal undoing the push, and the mock refusing a unix second where a block number belongs. The fork test reads the door and the block from the environment, and the front and the listing from the door; it is skipped unless `RPC_8453` and `EFFICIENT_PROP_DOOR` are set. Pin a block a few seconds after the listing's desk posted: once the post expires the door fills no size and the test fails. For a listing bound to a guarded source, run it at a block inside its lane's hold as well, where the quote and the fill both read the held print. The test walks a ladder of sizes in each direction through each mode and checks every fill against the door's own `quote` from the same state. It runs at gas price 0, so the quote and the fill both see a tip of 0; a pass does not show that a price source fills a real transaction at its quote. Forge reads `block.basefee` differently in a view call and in a state-changing call, so this test leaves the tip cap out.

The Ethereum fork test runs modes 0 and 1. It is skipped unless `RPC_1`, `EFFICIENT_PROP_ETH_DOOR` and `EFFICIENT_PROP_ETH_BLOCK` are set, the last a block in which the listing's entry landed: a fork at a block runs in that block's number and time, so the door's quote and the fill read the quote that block's entry wrote. There it walks a ladder of sizes in each direction, three to a power of ten, fills every size the door quotes and checks the fill against the quote and against the recipient's balance delta, and checks that exactly one `Swapped` was logged for the fill, by the listing's quote contract (the front's `deskCellOf` of the listing's desk) and not by the door, with the front's caller as sender (the door in mode 0, the adapter in mode 1) and the fill's tokens, amounts and recipient: the log a builder matches the fill by. A listing with a credit mode may fill no size of a side in a block (its custody empty and its route shut); the test logs that side and fails only where a quoted size does not fill. `EFFICIENT_PROP_ETH_NO_ENTRY_BLOCK` names a block in which the entry did not land and that is not the block right after an entry that set the carry bit (that block refuses with `StalePull()` or `AnchorExpired()`, not `NoWord()`): there, for every size the door quoted in the entry's block, the door's quote must revert `NoFill()` and the hop must revert the whole call with `NoWord()`, in each mode. The revert itself undoes the input's move and the approval, so the test checks nothing after it. The endpoint must serve the state at both blocks.

```sh
forge test --match-path 'test/adapters/efficient-prop/*' -vv
RPC_8453=<Base RPC> EFFICIENT_PROP_DOOR=<door> [EFFICIENT_PROP_BLOCK=<block>] \
  forge test --match-path 'test/adapters/efficient-prop/EfficientPropAdapterFork.t.sol' -vv
RPC_1=<Ethereum RPC> EFFICIENT_PROP_ETH_DOOR=<door> EFFICIENT_PROP_ETH_BLOCK=<block> \
  [EFFICIENT_PROP_ETH_NO_ENTRY_BLOCK=<block>] \
  forge test --match-path 'test/adapters/efficient-prop/EfficientPropAdapterEthFork.t.sol' -vv
forge fmt --check
```

The enclosing production Kyber router is outside this repository's adapter tests.
